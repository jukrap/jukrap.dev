# 채용 문서 운영 가이드

웹사이트와 채용 문서의 역할, 공개 연락처와 개인 연락처의 구분, PDF 갱신 절차를 정리합니다. 실제 문서 구성은 `src/data/documents/manifest.ts`와 문서 데이터가 기준입니다.

## 페이지와 문서의 역할

| 자료          | 담는 내용                                       | 현재 구성                             | 공개 범위       |
| ------------- | ----------------------------------------------- | ------------------------------------- | --------------- |
| About         | 경력·기술과 대표 업무의 짧은 소개               | 대표 업무에서 Work 상세로 연결        | 공개            |
| Work·Projects | 담당 범위, 구현 과정, 기술적 판단과 확인한 결과 | Work 대표 3개·추가 9개, Projects 전체 | 공개            |
| 포트폴리오    | 선별한 업무와 프로젝트의 기능·구현 내용         | 웹 문서 15쪽과 같은 디자인의 PDF      | 공개            |
| 이력서        | 경력·기술·주요 프로젝트 요약                    | 웹 문서 2쪽과 PDF                     | 공개, 검색 제외 |
| 경력기술서    | 회사 업무별 담당 범위와 구현 내용               | 웹 문서 2쪽과 PDF                     | 공개, 검색 제외 |

한국어와 영어로 각각 제공합니다. 페이지 수는 현재 구성에 따른 결과이며 고정 목표가 아닙니다. PDF는 A4에 내용을 압축하지 않고 웹 문서 각 쪽의 자연스러운 높이를 사용합니다.

포트폴리오는 정산 ERP, 물류 웹·출력 앱, 주식 업무 웹을 대표 사례로 다룹니다. 생활정보 앱·개인정보 보호 앱·AI 문서화 도구는 별도 상세 사례로, 그 밖의 회사 업무와 개인 프로젝트는 후속 페이지로 정리합니다. 문서별 선별 목록과 순서는 manifest에서 관리합니다.

기본 제출 조합은 이력서와 포트폴리오입니다. 경력기술서는 공고에서 요구하거나 담당 업무를 더 설명할 필요가 있을 때 함께 사용합니다. 웹사이트에는 문서보다 다양한 사례와 자세한 설명을 남깁니다.

## 문장 편집 기준

- About의 업무 요약은 핵심 구현을 한 문장으로 소개하고 담당 범위는 별도 줄에 표시합니다. 구현 과정과 측정 수치는 연결된 Work 상세에 둡니다.
- 완료한 작업은 과거형으로 씁니다. 현재의 개발 원칙이나 서비스 동작을 설명할 때는 문맥에 맞게 현재형을 사용합니다.
- 짧은 기능 목록에는 명사형을 사용할 수 있지만, 배경·판단·과정은 문장으로 설명합니다. 한 항목에 여러 설명을 길게 이어 붙이지 않습니다.
- 회사·기간·역할·기술·수치와 측정 조건은 보존합니다. 조사·제안, 개발 환경 확인, 운영 반영을 구분합니다.
- 한영 내용의 담당 범위와 사실관계를 맞춥니다. 모든 페이지에 같은 문장을 복사하기보다 각 페이지에 필요한 깊이로 설명합니다.

## 공개 연락처와 로컬 개인 연락처

포트폴리오·이력서·경력기술서는 운영 환경에서도 공개 연락처로 열립니다. 이력서와 경력기술서는 `noindex`를 적용하지만, 링크를 아는 사람은 접근할 수 있습니다. 검색 제외는 접근 제한이 아닙니다.

개인 연락처가 필요한 제출본은 로컬 개발 환경에서만 만듭니다. 프로젝트 루트의 `.env.local`에 다음 서버 환경 변수를 설정합니다. 실제 값은 저장소·문서·스크린샷에 기록하지 않으며 `NEXT_PUBLIC_` 접두사를 사용하지 않습니다.

- `PRIVATE_DOCUMENTS_ENABLED`
- `PRIVATE_RESUME_EMAIL`
- `PRIVATE_RESUME_PHONE`

개인 연락처는 개발 환경, localhost 요청, 명시적 활성화와 연락처 설정 조건을 모두 만족할 때만 표시됩니다. 운영 빌드와 Vercel에서는 개인 연락처 모드가 꺼집니다. 기본 개발 서버는 `127.0.0.1`에 바인딩됩니다.

문서 경로는 `/{locale}/portfolio`, `/{locale}/resume`, `/{locale}/career-brief`이며 locale은 `ko` 또는 `en`입니다. 개인 연락처가 포함된 PDF와 별도 제출본은 Git에서 제외된 로컬 폴더에 보관합니다.

## 공개 PDF 갱신

사이트의 다운로드 버튼은 `public/documents/`에 저장된 한영 PDF 6개를 제공합니다. 브라우저 인쇄 대화상자에서 만든 A4 파일과는 구분합니다.

1. 문서 본문·레이아웃·글꼴·이미지에 영향이 있는지 확인합니다. 공통 업무 데이터가 바뀌면 문서에 전달되는 내용도 대조합니다.
2. 문서가 바뀌었다면 운영 빌드를 로컬에서 실행하고, [PDF 생성 절차](../scripts/document-pdfs.md)에 따라 다시 생성합니다. 공개 PDF에는 개인 연락처를 넣지 않습니다.
3. 웹 문서와 PDF의 본문, 링크, 연락처와 페이지 수를 대조합니다. 한글 추출 순서, 글꼴 포함 여부, 페이지 경계와 이미지 잘림도 확인합니다.
4. 검수한 PDF를 관련 문서 변경과 함께 반영합니다. 중간 HTML·렌더러 프로필·검수 이미지는 공개 자산에 넣지 않습니다.

일반 사이트 문구만 바뀌고 웹 문서의 내용·디자인이 같다면 PDF를 다시 만들 필요가 없습니다. 이때는 문서 데이터와 기존 PDF가 보존됐는지 확인합니다.

## 제출 전 확인

- 이름, 기간, 담당 범위, 기술과 수치가 사이트·웹 문서·PDF에서 같은 사실을 가리키는지 대조합니다.
- PDF의 연락처와 링크를 확인하고, 텍스트를 복사했을 때 제목과 본문 순서가 자연스러운지 살펴봅니다.
- 공고에 맞춰 근거가 있는 경험을 선별합니다. 실제로 하지 않은 작업이나 사용하지 않은 기술을 추가하지 않습니다.
- 첨부 형식·파일 크기·필수 문서는 제출하는 공고와 플랫폼의 현재 안내를 확인합니다. 지원 경로가 다르면 요구 사항도 따로 확인합니다.
- 플랫폼에서 이력서를 변환하거나 구조화된 입력란을 제공하는 경우, 변환 결과와 입력 내용의 회사·기간·역할·기술명을 다시 확인합니다.
