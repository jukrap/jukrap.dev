# 채용 문서 운영 가이드

이 문서는 웹사이트와 채용 문서를 함께 관리할 때의 역할, 개인정보 경계, 출력·제출 절차를 정리한 운영 가이드입니다. 문서 구성이나 채용 플랫폼의 첨부 조건이 달라질 때 다시 확인합니다.

## 문서별 역할

| 자료        | 답해야 하는 질문               | 기본 형태                    | 공개 범위 |
| ----------- | ------------------------------ | ---------------------------- | --------- |
| 이력서      | 먼저 면접할 사람인가?          | A4 2쪽, ATS 친화적 단일 칼럼 | 비공개    |
| 경력기술서  | 회사에서 정확히 무엇을 맡았나? | A4 2쪽, 역할·결과·검증 중심  | 비공개    |
| 포트폴리오  | 어떤 기준으로 문제를 풀었나?   | A4 12쪽 공개 HTML            | 공개      |
| 개인 사이트 | 더 확인할 전체 근거가 있는가?  | Work 4+5와 Projects 전체     | 공개      |

기본 제출 조합은 **이력서 + 포트폴리오**입니다. 경력기술서는 공고에서 요구하거나 추가 파일 제출이 가능한 경우에만 사용합니다. 네 자료는 같은 사실을 바탕으로 하되, 문장을 서로 복제하지 않고 각 질문에 필요한 깊이만 담습니다.

## 로컬 개인정보 설정

비공개 문서는 프로젝트 루트의 `.env.local`에 아래 서버 환경 변수를 설정한 로컬 개발 환경에서만 엽니다. 실제 값은 저장소, 문서, 스크린샷에 기록하지 않으며 `NEXT_PUBLIC_` 접두사를 사용하지 않습니다.

- `PRIVATE_DOCUMENTS_ENABLED`
- `PRIVATE_RESUME_EMAIL`
- `PRIVATE_RESUME_PHONE`
- `PRIVATE_RESUME_BIRTH_YEAR`

기본 `npm run dev`는 private mode가 LAN에 노출되지 않도록 `127.0.0.1`에만 바인딩됩니다. 개발 서버가 `http://127.0.0.1:3000`에서 실행될 때 문서 주소는 다음과 같습니다.

- 공개 포트폴리오: `http://127.0.0.1:3000/ko/portfolio`
- 비공개 이력서: `http://127.0.0.1:3000/ko/resume`
- 비공개 경력기술서: `http://127.0.0.1:3000/ko/career-brief`

비공개 라우트는 로컬 private mode에서만 렌더링됩니다. 운영 빌드와 Vercel에서는 환경 변수 설정 여부와 관계없이 `/ko/resume`, `/ko/career-brief`가 404를 반환하며 검색·내비게이션·사이트맵에도 노출하지 않습니다.

## PDF 출력

브라우저에서 문서를 연 뒤 인쇄 대화상자를 다음처럼 설정합니다.

- 용지: A4 세로
- 배경 그래픽: 켜기
- 머리글과 바닥글: 끄기
- 배율: 기본값을 우선하고 페이지 수와 잘림을 확인한 뒤 조정
- 저장 위치: Git에서 제외된 `output/documents/`

저장 후에는 페이지 수(포트폴리오 12쪽, 이력서 2쪽, 경력기술서 2쪽), 한글 복사·검색 순서, 링크 클릭, 제목과 불릿의 페이지 잘림, 파일 크기를 확인합니다. 포트폴리오 9~11쪽의 프로젝트 이미지 5장도 빈 테두리로 출력되지 않았는지 전부 확인합니다. 개인정보가 포함된 이력서와 경력기술서 PDF는 공개 저장소나 PR 첨부 자료에 올리지 않습니다.

## 플랫폼 제출 체크리스트

### 공통

- 이름, 기간, 기술, 수치가 사이트와 각 문서에서 같은 사실을 가리키는지 확인합니다.
- PDF 안의 이메일·전화번호와 공개 링크가 최신인지 확인합니다.
- 모든 링크를 직접 열어 보고, 인쇄물에서도 URL의 대상을 식별할 수 있는지 확인합니다.
- PDF 텍스트를 복사해 제목과 본문 순서가 자연스러운지 확인합니다.
- 공고가 요구하지 않는 경력기술서는 기본 첨부에서 제외합니다.

### 공고별 10분 검수

- 공고에서 반복되는 업무와 요구 역량을 세 가지 이내로 먼저 적습니다.
- 이미 근거가 있는 경력 불릿과 프로젝트의 순서만 조정하고, 공고에 없는 경험을 새로 만들지 않습니다.
- 공고의 기술명과 문서의 기술명이 다르면 실제 사용한 범위 안에서 공식 표기로 맞춥니다.
- 회사, 기간, 역할, 수치와 검증 조건은 문서 원장과 다시 대조한 뒤 제출합니다.
- 웹 제품 중심 공고와 WebView·모바일 중심 공고처럼 실제 강점이 달라지는 경우에만 이력서 사본을 나눠 관리합니다.

### 원티드

- 자동 변환을 고려해 이력서는 단순한 제목 구조와 단일 칼럼을 유지합니다.
- 지원 포지션에 맞춘 이력서를 사용하되, 실제 근거가 없는 키워드는 추가하지 않습니다.
- 변환 후 경력 기간, 회사명, 프로젝트명, 기술명이 잘못 분리되지 않았는지 확인합니다.
- 세부 동작은 [원티드 이력서 변환 안내](https://help.wanted.co.kr/hc/ko/articles/46337426447897-%EC%9D%B4%EB%A0%A5%EC%84%9C-%EB%B3%80%ED%99%98%EC%9D%80-%EC%96%B4%EB%96%BB%EA%B2%8C-%ED%95%98%EB%82%98%EC%9A%94)를 기준으로 다시 확인합니다.

### 잡코리아

- 첨부 파일은 **개별 5MB 이하**로 유지합니다.
- 기본 이력서와 공개 포트폴리오를 우선 첨부하고, 공고 요구가 있을 때만 경력기술서를 추가합니다.
- 업로드 직전 제한은 [잡코리아 개인회원 FAQ](https://m.jobkorea.co.kr/help/faq/user)에서 다시 확인합니다.

### 사람인

- PDF만 첨부하지 않고 사이트의 구조화된 경력·스킬 입력란도 함께 작성합니다.
- 첨부 파일은 공고와 직접 관련된 이력서·포트폴리오를 선별하고, 경력기술서는 필요할 때만 추가합니다.
- 입력 항목과 첨부 방식은 [사람인 이력서 안내](https://www.saramin.co.kr/zf_user/help/help-word/main?inquiryCode=1639&memberCode=per)를 기준으로 확인합니다.

## 갱신 기준

회사·기간·역할·수치·프로젝트 URL은 사이트의 사실 원장을 먼저 고친 뒤 각 문서 표현을 동기화합니다. 레이아웃만 바뀌어도 PDF 페이지 수와 잘림을 다시 확인하고, 채용 플랫폼 정책은 제출 직전에 해당 안내 페이지에서 재확인합니다.
